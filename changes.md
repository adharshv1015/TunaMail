# Analysis of Analyst Explanation Discrepancy

Based on my investigation into the backend and frontend code, here is the issue causing the discrepancy in the Analyst Explanation between SUSPICIOUS and SAFE cases:

### 1. Frontend Data Source Mismatch
The frontend component (`frontend/src/components/email/AnalystExplanation.jsx`) reads from `decision.explanation`.
```javascript
const explanation = decision?.explanation || {};
```
This explanation is generated by `DecisionFusionEngine` (specifically the `_build_explanation` method in `backend/src/engines/decision_fusion_engine.py`).

However, the backend actually runs a dedicated `ExplanationEngine` (Stage 13) in `backend/src/api/gmail.py` which produces a highly detailed explanation (with `PRIMARY_REASON`, `NEGATIVE_EVIDENCE`, etc. grouped together). But instead of merging this into `decision.explanation`, `gmail.py` puts it in `analysis.explanation`:
```python
result["analysis"] = json_safe({
    ...
    "decision": decision_result,      # <--- Frontend reads this explanation
    "explanation": explanation,       # <--- ExplanationEngine output goes here and is ignored by AnalystExplanation.jsx
    ...
})
```

### 2. Why SUSPICIOUS shows nothing
Because the frontend relies on `DecisionFusionEngine`'s explanation, it only displays evidence from `structured_evidence` (deterministic engine rules). 
If an email is flagged as `SUSPICIOUS` primarily by the AI engine (e.g., Ollama) and not by deterministic rules, `structured_evidence` will be empty. 
- `negative_evidence` becomes `[]`
- `positive_evidence` becomes `[]`

The code sets `primary_reason` to `"Risk classification lacks explicit supporting evidence."`. However, this is likely being overwritten or cleared downstream (e.g., by `finalize_intelligence` or `consistency_validator` in `gmail.py`), resulting in a completely blank primary reason on the frontend.

### 3. Why SAFE shows Domain Mismatch
In `SAFE` cases, the deterministic engines (like `AuthenticationAnalyzer` or `URLAnalyzer`) execute and generate `structured_evidence`. 
If there's a slight mismatch between the `From` domain and the `Return-Path` or signature domain, a `"DOMAIN_MISMATCH"` (HIGH severity) or `"TLS_POLICY_VIOLATION"` (LOW severity) is added to the `negative_evidence` list. 
Since `decision.explanation.negative_evidence` successfully receives this array, the frontend maps over it and displays it, even though the overall fused verdict is `SAFE`.
